## Context

The ReAct loop is half-built: `TaskCommander` already runs reason → act → observe → terminate (`TestReActLoop` passes), the tracer emits `TaskTraced` as the single progress signal, the board assigns decision-tasks, and the postman forwards completion to the owner. What is missing to finish the architecture: the planner never emits a ReAct plan, the final answer is returned one-shot instead of streamed, reasoning is invisible to the user, and the loop lacks hardening.

## Goals / Non-Goals

**Goals:**
- Let a request select ReAct (request-driven, default Plan-Execute) and have the planner honor it.
- Stream only the final answer to the user over the dedicated protocol; keep all reasoning structured.
- Surface reasoning progress as user-visible telemetry.
- Harden the loop: max-steps, LLM-failure fallback, decision-task-failure termination.

**Non-Goals:**
- New ReAct reasoning strategies (tool selection, multi-agent delegation). The loop structure is fixed; content is the LLM's job.
- Stream every action's output — only the terminal answer streams.
- Planner-side ReAct heuristics (e.g. deciding architecture from prompt complexity). Architecture is request-driven.

## Decisions

### D1. Architecture is request-driven

`ChatRequest` gains an optional `Agent` field (`plan_execute` | `react`). The wrapper copies it into the raw task's `TaskPlan.Architecture`; the planner inherits it into the produced plan, defaulting to `plan_execute`. The commander already branches on it.

- **Alternatives considered**: global config flag. Rejected — the phone client chooses the agent per request (matches the lightweight-planner vision), and a config flag can still set the wrapper's default later.
- **Trade-off**: the request now carries a semantic field; the wrapper must validate it.

### D2. The commander streams the done answer

On a `done` decision, the commander starts a dedicated streaming synthesis call (`provider.Stream` with goal + trajectory as prompt), routes each `StreamChunkMsg` through the existing stream router, and accumulates the text. When the stream ends it publishes `TaskPlanDone` → wrapper → single `done` SSE frame. If streaming fails, it falls back to the decision's one-shot `answer`, then to concatenated outputs.

- **Alternatives considered**: streaming the last executor's output (the answer produced by an action). Rejected — the final answer is a synthesis over the whole trajectory, generated by the commander's LLM.
- **Trade-off**: one extra LLM call at the end. Acceptable — it is the only streamed generation.

### D3. Reasoning telemetry without leaking thoughts

Each iteration emits a status frame (iteration number + action summary) through the existing telemetry path; the raw reasoning prompt/response is never forwarded. This reuses `telemetry_bridge` → `TaskMonitor` unchanged.

- **Alternatives considered**: streaming the reasoning tokens. Rejected — leaks internal thought and floods the data plane.
- **Trade-off**: the user sees step counts, not the reasoning itself.

### D4. Loop hardening is local to the commander

- `maxSteps` default 10; reaching it finalizes with collected outputs.
- LLM-decision error / unparseable JSON → finalize with collected outputs.
- A decision-task reaching `TaskTraced Failed` → terminate the plan with `PlanError`.
All handled inside `reason()`/`onTraced`, no new components.

- **Alternatives considered**: a watchdog timeout per plan. Rejected for now — `maxSteps` bounds the loop; a wall-clock watchdog is future work.

### D5. Reuse the existing path for ReAct actions

Decision-tasks flow through `TaskReady` → board → executor → tracer, identical to Plan-Execute nodes. No new execution mechanism; ReAct differs only in how tasks are chosen (LLM) versus a static DAG.

- **Trade-off**: ReAct actions share the board's bid window latency. Acceptable — capability matching is the point.

## Risks / Trade-offs

- [Streaming adds an end-of-loop LLM call and latency] → Mitigation: fallback to one-shot answer/outputs on failure; the stream is the only visible latency.
- [Request-driven architecture means a malformed `Agent` value] → Mitigation: wrapper validates and defaults to `plan_execute`.
- [Trajectory grows with steps, inflating each reason prompt] → Mitigation: `maxSteps` bounds it; prompt truncation is future work.
- [Sequential ReAct (one action in flight) limits parallelism] → Mitigation: acceptable for Phase 2; parallel actions are a later extension.

## Migration Plan

1. Add `Agent` to `ChatRequest`; wrapper → raw task; planner → plan (default Plan-Execute). Additive, no behavior change.
2. Commander: reasoning telemetry + loop hardening (max-steps, fallback, failure). Existing `TestReActLoop` still passes.
3. Commander: stream the done answer via the stream router; fallback paths keep one-shot output.
4. Mock provider streams; extend the ReAct e2e to assert `status → step_result → stream → done`.
5. Rollback: `Agent` defaults to Plan-Execute, so ReAct is opt-in per request.

## Open Questions

- Should the answer-streaming synthesis prompt include the full trajectory or a condensed summary? Affects prompt size, not the contract.
- Does the client need a per-step indicator richer than an iteration count (e.g. tool name)? The telemetry payload can carry an action summary; decide during implementation.
